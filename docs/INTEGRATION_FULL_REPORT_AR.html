1. الملخص التنفيذي

كان المطلوب بناءُ واجهة استقبال موحّدة داخل مشروع unihub-API تُمكّن نظام الجامعة (Oracle) من دفع (Push) البيانات إلى نظامنا: إنشاء/تحديث/حذف — على الجداول الفعلية القائمة بكل أعمدتها وصفوفها، دون إنشاء جداول موازية، وبمستوى حماية مساوٍ أو أفضل من النموذج المرجعي في C:\xampp\htdocs\unihub\apis.

أُنجز العمل على ست مراحل متتابعة، والنتيجة النهائية نظام تكامل عام (config-driven):

محرّك عام

وصف كل جدول في ملف إعداد واحد، وإضافة أي جدول لاحقاً = مقطع في الإعداد فقط بلا كود إضافي.

حماية بعاملين

Bearer Token (مخزَّن hash ومقارَن بزمن ثابت) + قائمة IP مسموحة (مع منع التزوير). لا يُطلب ولا يُتحقّق من هيدر X-Client-MAC — إن أُرسل يُسجَّل في السجل فقط.

نجاح جزئي

الدفعة لا تُبطَل كاملة؛ كل صف خاطئ يُتخطّى مع سبب واضح في skipped_reasons.

تقوية كاملة

إعادة محاولة آمنة (Idempotency)، حدّ معدّل لكل عميل، سجلات وتقليم، وتوثيق شامل.

النتيجة المُتحقَّقة:
  • 102 اختباراً آلياً (PHPUnit) بنجاح كامل — 557 تأكيداً.
  • اختبار HTTP فعلي (Smoke) من طرف إلى طرف: 7/7 نجاح.
  • قاعدة البيانات الحقيقية نُظّفت بالكامل من بيانات الاختبار.

2. كيف يعمل الطلب (تدفّق الطلب)

كل طلب دفع يمرّ عبر هذه السلسلة بالترتيب. أي طبقة تفشل تُعيد ردًّا موحّدًا وتوقف السلسلة:

1) العميل (نظام الجامعة) → POST /api/external/v1/{resource} مع Authorization: Bearer
▼
2) حدّ عام مبدئي بحسب IP (throttle:integration-ip) — ضعف الحدّ الافتراضي
▼
3) مصادقة (integration.auth): نوع الطلب → التوكن → IP المصدر (حالة العميل) + تسجيل الطلب
▼ فشل → 401 / 403 / 405
4) حدّ المعدّل لكل عميل (integration.throttle) → 429 عند التجاوز
▼
5) إعادة المحاولة الآمنة (integration.idempotency) → إعادة رد مخزَّن أو 409
▼
6) المحرّك العام: تحقّق → حل المفاتيح → كشف التزاحم → Upsert/تعطيل (نجاح جزئي)
▼
7) رد موحّد + تحديث السجل (logs) + تخزين نتيجة Idempotency

3. طبقات الحماية الأمنية

طُبِّقت الحماية على عاملين مجتمعين (لا يكفي أحدهما)، بنفس فلسفة النموذج المرجعي، مع تقويات إضافية:

الطبقةالآليةأين تُنفَّذ
1. Bearer Token هيدر Authorization: Bearer <TOKEN>. التوكن يُخزَّن كـ hash (sha256) في قاعدة البيانات، ويُقارن بزمن ثابت (hash_equals) لمنع هجمات التوقيت. لا يُعرض إلا مرة واحدة عند الإنشاء. AuthenticateIntegrationClient
2. IP Whitelist عنوان IP المصدر ضمن قائمة مسموحة تدعم صيغة CIDR (مثل 10.0.0.0/24). لا يوجد فحص MAC (حقل allowed_macs خامل، وأُلغيت متطلبات X-Client-MAC). AuthenticateIntegrationClient
منع تزوير IP يُستخرج عنوان العميل من REMOTE_ADDR الفعلي، ولا يُقبل من ترويسات X-Forwarded-For إلا إذا فُعِّل الإعداد INTEGRATION_TRUST_FORWARDED_IP=true صراحةً (خلف وسيط موثوق). App\Support\ClientIp
تقييد الطرق يُسمح فقط بالطرق التي تُعدّل البيانات: POST / PUT / PATCH / DELETE. أي طريقة أخرى → 405. AuthenticateIntegrationClient
حدّ المعدّل حدّ لكل عميل (افتراضي 600 طلب/دقيقة، قابل للتجاوز لكل عميل) + حماية مبدئية بحسب IP قبل المصادقة. ThrottleIntegrationClient + AppServiceProvider
إعادة المحاولة الآمنة هيدر Idempotency-Key اختياري: نفس المفتاح + نفس الجسم → إعادة الرد المخزَّن حرفيًا؛ جسم مختلف بنفس المفتاح → 409. EnsureIdempotency
تسجيل كامل كل طلب يُسجَّل (IP، الحالة، مدة التنفيذ، ملخّص الرد، عيّنة من الحمولة — وترويسة X-Client-MAC إن وُجدت تُسجَّل ولا تُفحص) مع سياسة احتفاظ وتقليم تلقائي. AuthenticateIntegrationClient + integration:prune
حماية إضافية عامة وسيط CheckIpRestrictions العام يُطبَّق أيضًا على مسارات التكامل (قائمة سوداء/بيضاء من جدول ip_restrictions). CheckIpRestrictions
مقارنة بالنموذج المرجعي: في النموذج القديم كان التوكن ثابتًا داخل ملفات الكود وهيدر X-Client-MAC إلزاميًا وقابلًا للتزوير. هنا: التوكن في قاعدة البيانات كـ hash، وIP إلزامي، ومنع تزوير الترويسات، وسياسة قوائم فارغة = رفض (تشديد افتراضي) — وأُلغي فحص MAC نهائياً (لا يُطلب ولا يُتحقّق منه).

4. المسارات (Endpoints) وعقد الاستجابة

الطريقةالمسارالوظيفة
POST/api/external/v1/pingفحص الاتصال والمصادقة (ليس واجهة بيانات).
POST / PUT / PATCH/api/external/v1/{resource}إدخال/تحديث مجمّع (Upsert) — الجسم: { "data": [ ... ] }.
DELETE/api/external/v1/{resource}حذف/تعطيل حسب استراتيجية المورد.

لا توجد واجهات سحب (GET) — النظام يدفع البيانات فقط.

عقد الاستجابة الموحّد

{
  "status": "success",
  "message": "...",
  "timestamp": "2026-10-17 20:00:00",
  "inserted_records": 1,
  "updated_records": 0,
  "deactivated_records": 0,
  "skipped_records": 0,
  "skipped_reasons": [ "Row #1: ..." ]
}

الأساسية (15): colleges، departments، programs، levels، semesters، academic_titles، buildings، classrooms، days، periods، students، lecturers، courses، student_groups، timetable.

توسعة البنية الأكاديمية (18): blocks، block_relations، course_prerequisites، program_learning_outcomes، course_learning_outcomes، course_descriptions، course_topics، topic_questions، course_assignments، course_assessments، course_policies، course_references، assessment_methods، teaching_strategies، outcome_assessment_method، outcome_teaching_strategy، student_group_members، student_grades.

5. المراحل: ماذا نُفِّذ في كل مرحلة

I1 — الأساس الأمني مكتمل

  • جدولا integration_clients وintegration_logs.
  • وسيط المصادقة الثلاثية AuthenticateIntegrationClient.
  • كونترولر IntegrationController بنقطة ping ومجموعة مسارات /api/external/v1.
  • أمر إدارة العملاء integration:client.
  • ردود أخطاء موحّدة (401/403/405/404) لمسارات التكامل.

I2 — البيانات المرجعية الهيكلية مكتمل

  • بناء المحرّك العام IntegrationSyncService وجدول الربط integration_entity_refs.
  • تفعيل 10 موارد: الكليات، الأقسام، البرامج، المستويات، الفصول، الدرجات العلمية، المباني، القاعات، الأيام، الحصص.
  • Upsert بالمفتاح الطبيعي + حل المفاتيح الأجنبية بالأكواد + مراجع متداخلة (semester←level←program).
  • نجاح جزئي صف-بصف + استرجاع المحذوف ناعمًا.

I3 — الأشخاص (الطلاب وهيئة التدريس) مكتمل

  • ميزة linked_user: كتابة في جدولين (users + students/lecturers) وإنشاء الحساب تلقائيًا.
  • كلمة المرور الافتراضية 12345678 (تُطلب تغييرها عند أول دخول) — مطابقة للنظام الحالي.
  • الإيميل إلزامي ويأتي مع البيانات فقط (لا يُولَّد تلقائيًا).
  • حل المرجع المركّب title_code+college_id → title_id للدرجة العلمية.

I4 — المحتوى الأكاديمي (المقررات والمجموعات) مكتمل

  • موردا courses وstudent_groups.
  • دعم حقول JSON (مثل course_parts) + إعادة ترتيب الحل (foreign → parents → foreign_composite).
  • تعامل صحيح مع أعمدة NULL في المفتاح المركّب للمجموعات.

I5 — الجدول الدراسي مع كشف التزاحم مكتمل

  • مورد timetable بمفتاح طبيعي: (المجموعة + اليوم + الحصة + السنة الأكاديمية) + دعم external_id.
  • كشف تزاحم عام: أبعاد (محاضر/مجموعة/قاعة) + نطاق (يوم/حصة/سنة) + تقاطع التواريخ، مع استثناء السجل نفسه عند التحديث.
  • عند التزاحم: تخطّي الصف بسبب واضح. الحذف = status=0 (والمعطّل لا يمنع حجزًا جديدًا).

I6 — التقوية والتوثيق مكتمل

  • إعادة المحاولة الآمنة (Idempotency) بصلاحية 24 ساعة.
  • حدّ معدّل لكل عميل (افتراضي 600/دقيقة) + حماية IP مبدئية.
  • التقاط الحمولة + ملخّص الرد + سياسة احتفاظ 90 يومًا + أمر تقليم وجدولة يومية.
  • دليل Markdown + HTML جاهز للطباعة + مجموعة Postman + سكربتات اختبار HTTP.

إضافات هذه الجلسة (بعد I6)

  • تنظيف التوثيق: حذف ملفات التوثيق غير المتعلّقة بالتكامل داخل docs/.
  • تصليب ضد تزوير IP: أداة ClientIp + إعداد trust_forwarded_ip.
  • اختبارات آلية (PHPUnit): 7 مجموعات تغطّي الحماية والمزامنة والتزاحم وIdempotency والحدّ والتقليم.
  • اختبار HTTP (Smoke): سكربت PowerShell + ملف .http.

I7 — توسعة البنية الأكاديمية (18 مورداً) مكتمل

  • تفعيل 18 جدولاً عبر الكونفيج فقط: بلوكات وروابطها ومتطلبات المقررات؛ مخرجات التعلم (PLO/CLO)؛ محتوى المقرر (وصف/دروس/أسئلة)؛ التكليفات والتقويم والسياسات والمراجع؛ طرق التقويم واستراتيجيات التدريس وروابط المخرجات؛ عضوية المجموعات ودرجات الطلاب.
  • توسعة المحرّك: نوع حذف hard_delete (جداول الروابط) + دعم المفتاح المركّب (student_group_members: student_id+group_id).
  • دعم foreign_composite مع nullable، وselect في foreign/foreign_via_user، وتجاوز null في قيم enum القابلة للإفراغ.
  • اختبارات المراحل: 102 اختباراً في tests/Feature/Integration بصفر فشل.

13. كيف تُضيف جدولاً جديداً؟

بفضل التصميم القائم على الإعداد، لا تحتاج كودًا جديدًا. أضف مقطعًا واحدًا في config/integration.php ضمن resources:

'resources' => [
    // ...
    'my_table' => [
        'table'       => 'my_table',            // الجدول الحقيقي
        'primary_key' => 'id',
        'writable'    => ['code', 'name', 'college_code'],
        'required'    => ['code', 'name'],
        'defaults'    => ['is_active' => 1],
        'casts'       => ['is_active' => 'bool'],
        'foreign'     => ['college_code' => ['colleges', 'college_code', 'college_id']],
        'match'       => ['code'],              // المفتاح الطبيعي
        'deactivate'  => ['column' => 'is_active', 'value' => 0],
    ],
];

يصبح المورد متاحًا فورًا عبر /api/external/v1/my_table بكل ميزات المحرّك (حل المفاتيح، النجاح الجزئي، الحذف، التسجيل).

14. الملاحظات والحدود

  • لا واجهات سحب (GET): النظام يدفع فقط، حسب الاتفاق.
  • الإيميل إلزامي: يأتي ضمن البيانات، ولا يُولَّد تلقائيًا.
  • حذف ناعم/تعطيل: حسب أعمدة كل جدول (is_active أو status أو deleted_at).
  • نجاح جزئي: لا تُبطَل الدفعة كاملة؛ الصفوف الخاطئة تُتخطّى بأسباب واضحة.
  • إعداد Trusted Proxies: إن كان النظام خلف وسيط موثوق، فعّل INTEGRATION_TRUST_FORWARDED_IP=true فقط حينها.
  • التنبيهات (deprecations): مصدرها إعداد Laravel الافتراضي لقاعدة PostgreSQL، ولا تؤثّر على التكامل.
  • الحالة في Git: كل تغييرات التكامل غير مُودَعة (uncommitted)؛ يُنصح بمراجعتها ثم عمل commit.
